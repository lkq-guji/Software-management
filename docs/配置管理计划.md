## 4. 变更申请与审批流
1. **申请**：提出变更目的、影响文件、期望效果和风险；缺陷可以先建 Issue。
2. **评估**：组长检查配置项、影响范围、冲突风险及开发人员的职责边界。
3. **实施**：由负责成员在自己分支进行修改，运行并保存实际测试输出。
4. **提交**：仅提交职责内文件，使用规范提交信息（如 `docs:`/`feat:`/`test:`），推送并创建 PR 指向 `main`。
5. **审核**：组长逐个检查提交作者、文件范围、运行结果、兼容性、代码安全、PR 描述；未通过则要求作者修改。
6. **合并及跟踪**：评审通过后才由组长合并 PR，登记 PR 链接、合并提交和复核结果到变更记录。
7. **发布**：所有组员真实完成且集成测试通过后再创建 `v1.0.0` 标签。

## 5. PR 审查准入条件
- PR 目标必须是 `main`，来源为对应负责人分支，提交作者为实际操作者。
- 变更内容对应本人任务，不能覆盖其他人未合并工作或加入个人资料、密码、密钥。
- 提供 PR 摘要、相关任务、运行命令、测试结果；文档变更须检查格式与事实准确性。
- 功能与测试代码变更至少执行 `python -m unittest discover -s tests -v`，不通过则不得合并。
- CI 如果已配置，必须检查相关检查结果；无 CI 时不能写“CI已通过”。
- 发现冲突交由原分支作者解决，不以强推、硬重置绕过。
- 组长自己的 PR 同样保留待审核状态；本计划不授权自动合并该 PR。
